# Phase 15.5: UIKit Keyboard Rebuild (Issue #59) - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Rebuild the keyboard key layer from SwiftUI to UIKit to eliminate dead zones between keys. Each key becomes a `UIButton` subclass with `point(inside:with:)` override to extend touch areas beyond visual bounds, covering 100% of the keyboard surface. Only the key buttons change -- everything else (toolbar, recording overlay, emoji picker, KeyboardState, dictation, waveform) stays SwiftUI.

</domain>

<decisions>
## Implementation Decisions

### Touch surface strategy
- Each key is a `UIButton` subclass with `point(inside:with:)` override using negative `UIEdgeInsets` to extend touch area beyond visual bounds
- Touch insets extend to cover half the gap towards each neighbor -- overlapping hit regions ensure zero dead zones
- Remove the existing dead zone catch-all (`handleDeadZoneTap`) entirely -- `point(inside:with:)` makes it unnecessary
- Preserve touchDown audio + haptic (from Phase 15.3): fire on `touchesBegan`, not `touchesEnded`

### Architecture (from Issue #59)
- `KeyboardRootView` (SwiftUI) stays as container -- no changes
- New `KeyboardUIView` (UIViewRepresentable) wraps the UIKit keyboard layer
- Vertical `UIStackView` for rows, horizontal `UIStackView` per row, `KeyButton` instances as arranged subviews
- Reuse `KeyboardLayout.swift` as data source for key definitions
- Reuse `KeyMetrics` for all spacing/sizing constants
- Reuse `HapticFeedback`, `KeyTapSignposter`, `AccentedCharacters` as-is

### Key popup & accent UX
- Key popups (press preview + accent strip) stay as **SwiftUI overlays** in KeyboardRootView's ZStack above the UIKit layer
- Shared `ObservableObject` bridge (e.g., `KeyboardTouchState`) for UIKit buttons to report press state/position to SwiftUI popup layer
- Accent long-press uses **UIKit UIPanGestureRecognizer** on the key button (touch starts and stays in UIKit)
- Accent popup appearance/position/timing kept **identical** to current (400ms delay, 36pt cell width, horizontal strip above key)

### Visual style
- Skip Liquid Glass (`dictusGlass` modifier) -- use simpler UIKit **rounded rect backgrounds** with adaptive colors
- Use `UIColor` dynamic colors (`.secondarySystemBackground`, `.label`, etc.) for **automatic dark/light mode** support
- Press animation on letter keys: match current exactly (slight dim + popup above)
- Special keys (delete, space, return): **background color change on press** preserved (brighter in dark mode, darker in light mode) -- from Phase 15.3
- Shift key icon states (empty/filled/lock) and symbol toggle label transform ("123"/"ABC") preserved

### Trackpad mode (space bar)
- Replace SwiftUI DragGesture with **UIPanGestureRecognizer** on space button
- Long-press activates trackpad mode, pan moves cursor
- Keep identical sensitivity and behavior -- pure port, no tuning

### Delete repeat
- Keep current **Task.sleep async loop** pattern for accelerating delete repeat
- Triggered from `touchesBegan` instead of SwiftUI DragGesture `.onChanged`
- Keep identical acceleration curve -- pure port, no tuning

### Migration strategy
- **Big bang**: all keys (letter + special) rebuilt in UIKit in one phase
- **Delete old SwiftUI key code**: KeyButton.swift, SpecialKeyButton.swift, KeyRow.swift replaced (git history is the fallback)
- Work on `feature/uikit-keyboard-rebuild` branch (current branch or new one)
- Code organized per Issue #59 architecture diagram

### Claude's Discretion
- Exact UIEdgeInsets values for touch extension per key type
- UIStackView configuration (distribution, alignment, spacing)
- How to structure the ObservableObject bridge (what properties, update frequency)
- Whether to pre-compute key frames at layout time or compute dynamically
- Whether to reuse ProximityGrid/KeyFrame/KeyDecoder from git history (commits 83767f6..f201d1a)
- Exact UIColor values for key backgrounds and press states

</decisions>

## Existing Code Insights

- `KeyMetrics` enum -- all spacing constants (keyHeight, rowSpacing, keySpacing, rowSidePadding, keyCornerRadius) with 3 device classes
- `DeviceClass` enum -- compact/standard/large breakpoints at 667/852pt screen height
- `KeyboardLayout` -- AZERTY/QWERTY row definitions as `[[KeyDefinition]]`
- `KeyDefinition` -- key type, label, output, widthMultiplier
- `AccentedCharacters` -- accent data per key for long-press
- `HapticFeedback` -- pre-allocated UIImpactFeedbackGenerator instances with prepare() pattern
- `KeySound` enum -- system sound IDs (letter: 1104, delete: 1155, modifier: 1156)
- `KeyTapSignposter` -- OSSignposter for Instruments profiling

### Established Patterns
- `DictusCore` shared framework for cross-target code
- `#if canImport(UIKit) && !os(macOS)` guards for test compatibility
- `ObservableObject` for state bridging (KeyboardState pattern)
- Pre-allocated static instances (haptic generators, cached UserDefaults)

### Integration Points
- `KeyboardRootView.body` ZStack -- new `KeyboardUIView` replaces current keyboard VStack
- `KeyboardView.insertCharacter()` pipeline -- audio/haptic/text insertion logic moves to UIKit button actions
- `SuggestionState.update(proxy:)` -- called after keystroke, already on background queue (Phase 15.3)
- `KeyboardViewController.textDocumentProxy` -- UIKit buttons need access for text insertion

## Specific Ideas

- User chose UIButton subclass approach (option 1 from issue #59) over single-UIView (option 2) or hybrid (option 3) during Phase 15.4 debugging
- `point(inside:with:)` with negative UIEdgeInsets is the standard iOS technique since iOS 5 -- Apple uses it natively (patent US8232973B2)
- Previous Phase 15.4 proved SwiftUI catch-all insufficient after 16+ micro-tests -- this is the definitive solution
- User explicitly wants to delete old SwiftUI key code (not keep commented or on branch) -- git history is sufficient fallback
