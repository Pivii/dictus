# Phase 15.5: UIKit Keyboard Rebuild - Research

**Researched:** 2026-03-25
**Domain:** UIKit keyboard extension -- UIButton subclass with extended hit regions via `point(inside:with:)`
**Confidence:** HIGH

## Summary

This phase rebuilds the keyboard key layer from SwiftUI to UIKit to eliminate dead zones between keys. Phase 15.4 proved conclusively (16+ micro-tests) that SwiftUI has no mechanism to extend a view's hit-test area beyond its layout bounds. The solution uses `UIButton` subclass with `point(inside:with:)` override -- the standard iOS technique since iOS 5, used natively by Apple (patent US8232973B2).

The scope is well-bounded: only the key buttons change. Everything else (KeyboardRootView, toolbar, recording overlay, emoji picker, KeyboardState, dictation, waveform) stays SwiftUI. The new UIKit keyboard layer is embedded via `UIViewRepresentable`. Key popups and accent strips remain as SwiftUI overlays, communicated via an `ObservableObject` bridge.

**Primary recommendation:** Build a `UIViewRepresentable` wrapper containing vertical `UIStackView` of row `UIStackView`s, each containing `KeyButton: UIButton` subclasses. Each button overrides `point(inside:with:)` with negative `UIEdgeInsets` to extend touch area to cover half the gap to each neighbor. Reuse `KeyMetrics`, `KeyboardLayout`, `KeyDefinition`, `HapticFeedback`, `AccentedCharacters`, and `KeyTapSignposter` as-is.

### Pattern 1: UIButton subclass with extended hit region
**What:** Override `point(inside:with:)` to extend touch area beyond visual bounds
**When to use:** Every key button
**Example:**
```swift
// Source: Apple documentation UIView.point(inside:with:)
// https://developer.apple.com/documentation/uikit/uiview/1622533-point
class LetterKeyButton: UIButton {
    /// Negative insets expand the touch area beyond visual bounds.
    /// Values are computed at layout time based on gap to neighbors.
    var touchInsets = UIEdgeInsets(top: -5, left: -3, bottom: -5, right: -3)

    override func point(inside point: CGPoint, with event: UIEvent?) -> Bool {
        let expandedBounds = bounds.inset(by: touchInsets)
        return expandedBounds.contains(point)
    }
}
```

**Critical detail:** `UIEdgeInsets` with NEGATIVE values EXPAND the rect (unlike padding which shrinks). `bounds.inset(by: UIEdgeInsets(top: -5, ...))` creates a rect that is 5pt taller on top. This is the exact inverse of what the name suggests -- a common source of bugs.

### Pattern 2: UIViewRepresentable bridge
**What:** Wrap UIKit keyboard view for embedding in SwiftUI hierarchy
**When to use:** KeyboardUIView wrapping the UIKit container
**Example:**
```swift
struct KeyboardUIView: UIViewRepresentable {
    let rows: [[KeyDefinition]]
    let isShifted: Bool
    let rowWidth: CGFloat
    @ObservedObject var touchState: KeyboardTouchState
    // ... action callbacks

    func makeUIView(context: Context) -> KeyboardContainerView {
        let container = KeyboardContainerView()
        container.configure(rows: rows, rowWidth: rowWidth, ...)
        return container
    }

    func updateUIView(_ uiView: KeyboardContainerView, context: Context) {
        // Update shift state, layer changes, etc.
        uiView.updateShiftState(isShifted)
    }
}
```

### Pattern 3: ObservableObject bridge for popup state
**What:** UIKit buttons publish press state for SwiftUI popup overlay
**When to use:** Key popup preview and accent popup positioning
**Example:**
```swift
class KeyboardTouchState: ObservableObject {
    @Published var pressedKeyLabel: String? = nil
```

**Performance note:** Limit @Published updates to visual-only state changes (press/release, accent show/hide). Do NOT publish every touch move -- only accent selection index changes during drag.

### Pattern 4: touchesBegan/touchesEnded for immediate feedback
**What:** Override `touchesBegan` on UIButton for touchDown feedback (audio + haptic)
**When to use:** All key types -- matches Apple keyboard behavior (Phase 15.3 decision)
**Example:**
```swift
override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent?) {
    super.touchesBegan(touches, with: event)
    // Immediate visual + audio + haptic on touch down
    AudioServicesPlaySystemSound(KeySound.letter)
    HapticFeedback.keyTapped()
    HapticFeedback.prepareForNextTap()
    onPressStateChanged?(true)
}

override func touchesEnded(_ touches: Set<UITouch>, with event: UIEvent?) {
    super.touchesEnded(touches, with: event)
    onPressStateChanged?(false)
    onTap?(outputChar)
}

override func touchesCancelled(_ touches: Set<UITouch>, with event: UIEvent?) {
    super.touchesCancelled(touches, with: event)
    onPressStateChanged?(false)
    // No character insertion on cancel
}
```

### Pattern 5: UIStackView layout with zero spacing
**What:** Vertical + horizontal UIStackViews with spacing 0, visual gaps via background insets
**When to use:** Keyboard row layout -- matches current SwiftUI HStack(spacing: 0) approach
**Example:**
```swift
let rowStack = UIStackView()
rowStack.axis = .horizontal
rowStack.spacing = 0
rowStack.distribution = .fill  // Keys have explicit width constraints
rowStack.alignment = .fill     // Keys fill full row height
```

**Why .fill distribution:** Each key has a different width based on `widthMultiplier`. Using `.fill` with explicit width constraints lets each key be precisely sized. `.fillEqually` would make all keys the same width.

### Anti-Patterns to Avoid
- **UIView.hitTest override on container:** Don't override `hitTest(_:with:)` on the parent container view. Use `point(inside:with:)` on individual buttons instead. `hitTest` traverses the view hierarchy top-down; `point(inside:)` extends individual button bounds cleanly.
- **translatesAutoresizingMaskIntoConstraints on inputView:** Do NOT set this to false on `kbInputView` (the UIInputView). iOS manages its frame via autoresizing masks. Only set it false on child views you add programmatically.
- **Excessive ObservableObject updates:** Don't publish on every touch move event. Only publish when popup state actually changes (key press, key release, accent index change).
- **UIControl addTarget for touchDown:** Don't use `.touchDown` control event -- it fires too late in the responder chain compared to `touchesBegan`. Override `touchesBegan` directly for minimum latency.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Touch inset calculation | Custom geometry engine | `point(inside:with:)` + simple UIEdgeInsets | Apple's native hit-testing, handles edge cases like overlapping views |
| Key layout sizing | Custom frame math | UIStackView + width constraints | Auto Layout handles rotation, device classes cleanly |
| Keyboard sounds | AVAudioPlayer / custom audio | `AudioServicesPlaySystemSound(KeySound.*)` | Already working, respects silent switch, 3 distinct sounds |
| Haptic feedback | Custom UIFeedbackGenerator | `HapticFeedback.*` from DictusCore | Pre-allocated generators with prepare() pattern already built |
| Dynamic colors | Manual dark/light checks | `UIColor { traitCollection in ... }` or system colors | Automatic trait collection updates |
| Key data model | New key struct | `KeyDefinition` + `KeyboardLayout` | Already defines all keys, rows, width multipliers for AZERTY/QWERTY/numbers/symbols |

**Key insight:** The existing codebase already solved all the hard problems (layout data, haptics, sounds, accent data, signposting). This phase is a UI layer swap, not a feature rebuild.

## Common Pitfalls

### Pitfall 1: UIEdgeInsets sign confusion
**What goes wrong:** Positive insets SHRINK the rect, negative insets EXPAND it. Developers often get this backwards.
**Why it happens:** The API name `inset(by:)` implies shrinking, but negative values reverse the direction.
**How to avoid:** Always test with a simple assertion: `bounds.inset(by: UIEdgeInsets(top: -5, left: -3, bottom: -5, right: -3)).contains(CGPoint(x: -2, y: -2))` should be `true`.
**Warning signs:** Keys still have dead zones after implementation; taps at edges don't register.

### Pitfall 2: UIViewRepresentable updateUIView called too frequently
**What goes wrong:** SwiftUI calls `updateUIView` on every state change in parent. Rebuilding the entire UIKit keyboard on every keystroke kills performance.
**Why it happens:** SwiftUI's diffing doesn't understand UIKit views -- it calls update when any observed state changes.
**How to avoid:** Only update what changed. Track previous state in Coordinator. Use `context.coordinator.previousShiftState` etc. to skip no-op updates. Avoid recreating UIStackViews in `updateUIView` -- create them once in `makeUIView`, update labels/colors in `updateUIView`.
**Warning signs:** Keyboard feels sluggish on fast typing, Instruments shows repeated layout passes.

### Pitfall 3: touchesCancelled not handled
**What goes wrong:** If the user starts a touch on a key and iOS cancels it (e.g., system gesture, notification), the button stays visually pressed forever.
**Why it happens:** Developers implement `touchesBegan`/`touchesEnded` but forget `touchesCancelled`.
**How to avoid:** Always implement `touchesCancelled` with the same cleanup as `touchesEnded` (minus character insertion).
**Warning signs:** Keys occasionally get "stuck" in pressed state after system interruptions.

### Pitfall 4: Keyboard extension memory limit (~50MB)
**What goes wrong:** Creating too many UIView objects or caching too many layers can exceed the extension memory limit.
**Why it happens:** Each UIButton has a CALayer, shadow layers add memory, and keyboard extensions are strictly limited.
**How to avoid:** Use `shadow(color:radius:x:y:)` sparingly (or use a single shadow path). Pre-compute shadows at layout time. The current keyboard has ~30 keys across 4 layers -- this is fine. Don't pre-create views for all 4 layers; create/swap on layer change.
**Warning signs:** Extension killed by iOS (no crash log, just disappears).

### Pitfall 5: textDocumentProxy access from UIKit callbacks
**What goes wrong:** UIKit button action callbacks need `textDocumentProxy` to insert text, but the proxy reference must come from the `UIInputViewController`.
**Why it happens:** UIKit buttons don't have SwiftUI's environment access. The proxy reference must be explicitly passed through.
**How to avoid:** Pass the proxy (or a callback closure that captures it) from KeyboardUIView -> UIViewRepresentable -> Coordinator -> button actions. The current SwiftUI code passes `controller.textDocumentProxy` -- the UIKit code needs the same reference chain.
**Warning signs:** Crash on text insertion, nil proxy references.

### Pitfall 6: Layer switching with UIKit views
**What goes wrong:** Switching from letters to numbers/symbols requires rebuilding all buttons (different keys, different widths).
**Why it happens:** Unlike SwiftUI's declarative re-render, UIKit views must be explicitly removed and recreated.
**How to avoid:** Implement a `rebuildKeys(rows:)` method on the container that removes all arranged subviews from row stacks and creates new ones. OR: pre-build all layers and toggle `isHidden`. The former is simpler and uses less memory (keyboard extension constraint).
**Warning signs:** Stale keys visible after layer switch, layout breaks on numbers/symbols layer.

### Pitfall 7: Shift state visual update without full rebuild
**What goes wrong:** Toggling shift should uppercase all letter labels. If you rebuild the entire keyboard on shift toggle, it causes visible flicker.
**Why it happens:** Letter keys need label updates (a -> A) but the view hierarchy should not be recreated.
**How to avoid:** Store references to letter key buttons. On shift toggle, iterate and update `setTitle(_:for:)` or update the custom label. This is an `updateUIView` operation, not a full rebuild.
**Warning signs:** Visible flicker on shift tap, keys briefly disappear.

### Pitfall 8: GeometryReader width timing
**What goes wrong:** The UIViewRepresentable needs `rowWidth` from GeometryReader, but GeometryReader can report 0 or wrong width on first layout pass.
**Why it happens:** SwiftUI layout happens in passes; GeometryReader may not have final width during `makeUIView`.
**How to avoid:** In `updateUIView`, check if width changed and re-layout. Or use `viewDidLayoutSubviews`-equivalent in the UIView to self-size based on `bounds.width`.
**Warning signs:** Keys have zero width on first appearance, keyboard flashes before correct layout.

## Code Examples

### Computing touch insets per key
```swift
// After layout, compute touch insets based on gap to neighbors
func computeTouchInsets(for button: KeyButton, in rowStack: UIStackView) {
    let views = rowStack.arrangedSubviews
    guard let index = views.firstIndex(of: button) else { return }

    // Vertical: extend to cover half of rowSpacing above and below
    let verticalExtension = KeyMetrics.rowSpacing / 2

    // Horizontal: extend to cover half of gap to neighbor
    // For edge keys, extend to keyboard edge
    let leftExtension: CGFloat
    let rightExtension: CGFloat

    if index == 0 {
        // Leftmost key: extend to keyboard left edge
        leftExtension = button.frame.minX
    } else {
        let prevButton = views[index - 1]
        leftExtension = (button.frame.minX - prevButton.frame.maxX) / 2
    }

    if index == views.count - 1 {
        // Rightmost key: extend to keyboard right edge
        rightExtension = rowStack.bounds.width - button.frame.maxX
    } else {
        let nextButton = views[index + 1]
        rightExtension = (nextButton.frame.minX - button.frame.maxX) / 2
    }

    // Negative values expand the touch area
    button.touchInsets = UIEdgeInsets(
        top: -verticalExtension,
        left: -leftExtension,
        bottom: -verticalExtension,
        right: -rightExtension
    )
}
```

### Delete key with Task.sleep repeat (UIKit port)
```swift
// Port of existing DeleteKey pattern from touchesBegan
override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent?) {
    super.touchesBegan(touches, with: event)
    isHolding = true
    onDelete?()  // Immediate first delete
    HapticFeedback.keyTapped()
    AudioServicesPlaySystemSound(KeySound.delete)
    deleteCount = 1

    repeatTask = Task { @MainActor in
        try? await Task.sleep(nanoseconds: 400_000_000)  // Initial delay
        while !Task.isCancelled {
            if self.deleteCount >= 10 {
                self.onWordDelete?()
            } else {
                self.onDelete?()
            }
            HapticFeedback.keyTapped()
            AudioServicesPlaySystemSound(KeySound.delete)
            let interval: UInt64 = self.deleteCount >= 10 ? 120_000_000 : 100_000_000
            try? await Task.sleep(nanoseconds: interval)
            self.deleteCount += 1
        }
    }
}
```

```swift
// On the letter key button, add a UIPanGestureRecognizer
let panGesture = UIPanGestureRecognizer(target: self, action: #selector(handleAccentPan(_:)))
addGestureRecognizer(panGesture)

// 400ms timer triggers accent mode
longPressTimer = Task { @MainActor in
    try? await Task.sleep(nanoseconds: 400_000_000)
    guard !Task.isCancelled else { return }
    self.longPressFired = true

    guard longPressFired else { return }

}
```

## State of the Art

| Old Approach (Current) | New Approach (This Phase) | Why |
|------------------------|---------------------------|-----|
| SwiftUI DragGesture(minimumDistance: 0) | UIButton.touchesBegan/touchesEnded | Full control over hit-testing via point(inside:with:) |
| SwiftUI `.contentShape(Rectangle())` | UIButton `point(inside:with:)` override | SwiftUI contentShape clips to parent bounds; UIKit point(inside:) has no such limitation |
| SwiftUI `HStack(spacing: 0)` + background padding | UIStackView(spacing: 0) + background insets | Same visual result, but UIKit buttons can extend touch area beyond their frame |
| SwiftUI conditional rendering (if/else) | UIKit view visibility toggle or rebuild | Layer switching (letters/numbers/symbols) |
| `.dictusGlass()` modifier | Rounded rect with `UIColor` dynamic colors | Simpler, lower memory, no iOS 26 dependency for keyboard keys |

**Key insight:** This is NOT a downgrade from SwiftUI to UIKit. It is using the right tool for the job. SwiftUI excels at declarative UI composition (overlays, animations, state management) but cannot extend hit-test areas. UIKit excels at precise touch handling. The hybrid approach (UIKit keys inside SwiftUI container) gets the best of both.

## Decision Recommendations (Claude's Discretion)

### Touch inset values
**Recommendation:** Compute dynamically at layout time based on actual gaps between keys. Do NOT hardcode fixed values.
- Vertical insets: `KeyMetrics.rowSpacing / 2` (5.5pt on standard devices)
- Horizontal insets for letter keys: `KeyMetrics.keySpacing / 2` (3pt on standard)
- Edge keys: extend to keyboard edge (variable, computed from frame position)
- Row 3 special keys (shift/delete at 1.5x width): same formula applies
- Row 4 keys (space at 4.5x): computed from actual gap

**Confidence:** HIGH -- this is straightforward geometry.

### UIStackView configuration
**Recommendation:**
- Vertical stack: `axis: .vertical`, `spacing: 0`, `distribution: .fillEqually`, `alignment: .fill`
- Horizontal stacks: `axis: .horizontal`, `spacing: 0`, `distribution: .fill`, `alignment: .fill`
- Keys get explicit width constraints: `widthAnchor.constraint(equalTo: rowStack.widthAnchor, multiplier: key.widthMultiplier / totalMultiplier)`

**Why .fillEqually for vertical:** All rows are the same height (`keyHeight + rowSpacing`).
**Why .fill for horizontal:** Keys have different widths based on `widthMultiplier`.

**Confidence:** HIGH -- standard UIStackView usage.

### ObservableObject bridge structure
**Recommendation:** Single `KeyboardTouchState` class with minimal published properties:
```swift
class KeyboardTouchState: ObservableObject {
    // Key press popup
    @Published var pressedKeyLabel: String?
    @Published var pressedKeyFrame: CGRect = .zero  // In keyboard coordinate space

    // Accent popup
    @Published var showingAccents: Bool = false
    @Published var accentOptions: [String] = []
    @Published var selectedAccentIndex: Int?
    @Published var accentKeyFrame: CGRect = .zero  // Position for accent popup

    // Trackpad overlay
    @Published var isTrackpadActive: Bool = false
}
```
Update frequency: Only on state transitions (press/release = 2 updates per keystroke, accent index = on finger move during accent mode only).

**Confidence:** MEDIUM -- may need tuning based on SwiftUI re-render performance.

### Pre-compute vs dynamic key frames
**Recommendation:** Pre-compute after layout. Store button references in arrays for O(1) access. Recompute touch insets in `layoutSubviews()` override on the container view (fires on rotation, size change).

**Confidence:** HIGH -- `layoutSubviews` is the standard UIKit hook for this.

### Reuse ProximityGrid/KeyDecoder from git history
**Recommendation:** Do NOT reuse. The `point(inside:with:)` approach makes ProximityGrid/KeyDecoder unnecessary. Those were built for a single-UIView approach where one view needed to decode touches to keys. With individual UIButton subclasses, iOS's hit-testing does the work natively. The whole point of the UIButton approach is to leverage iOS's built-in view hit-testing rather than reimplementing it.

**Confidence:** HIGH -- using UIButton eliminates the need for custom spatial indexing.

### UIColor values for key backgrounds
**Recommendation:** Port existing `KeyMetrics` colors to UIColor:
```swift
// Letter key background (already defined as UIColor inside Color wrapper)
static let letterKeyBackground = UIColor { tc in
    tc.userInterfaceStyle == .dark
        ? UIColor(white: 0.22, alpha: 1)
        : .white
}

// Pressed special key background
static let pressedKeyBackground = UIColor { tc in
    tc.userInterfaceStyle == .dark
        ? UIColor(white: 0.32, alpha: 1)
        : UIColor(white: 0.88, alpha: 1)
}
```
These are the exact same values currently in `KeyMetrics.letterKeyColor` and `KeyMetrics.pressedKeyColor`, just without the SwiftUI `Color()` wrapper.

**Confidence:** HIGH -- direct port of existing values.

## Integration Points (Critical)

### 1. KeyboardRootView modifications
The current `KeyboardRootView` calls `KeyboardView(controller:hasFullAccess:isEmojiMode:suggestionState:initialLayer:)`. This will change to call `KeyboardUIView(...)` instead, with popup overlays in the same ZStack.

### 2. textDocumentProxy access chain
Current: `controller.textDocumentProxy` accessed in SwiftUI closures.
New: Must be passed through UIViewRepresentable Coordinator to UIKit button action closures.
Pattern: `KeyboardUIView.Coordinator` holds weak reference to controller, provides closure-based API to buttons.

### 3. SuggestionState updates
Current: `suggestionState.updateAsync(context:)` called from `insertCharacter()` in KeyboardView.
New: Same calls, but triggered from UIKit button callbacks through the Coordinator.

### 4. KeyboardLayerType management
Current: `@State currentLayer` in KeyboardView drives conditional rendering.
New: Layer state lives in the UIViewRepresentable bridge or Coordinator. Layer switch triggers `rebuildKeys()` on the UIKit container.

### 5. Height calculation
Current: `KeyboardView.keyboardHeight` and `KeyboardViewController.computeKeyboardHeight()` must agree.
New: Same calculation. The UIKit container view should use the same `KeyMetrics` constants. No height change expected.

## Open Questions

1. **Key popup clipping at top of keyboard**
   - What we know: iOS keyboard extensions cannot draw above their top edge. Current `kbInputView.clipsToBounds = false` is set but iOS may re-enforce it.
   - What's unclear: Whether UIKit popup views behave differently than SwiftUI overlays for top-row key popups.
   - Recommendation: Keep popups as SwiftUI overlays in KeyboardRootView ZStack (they already work). If clipping persists, offset popup downward for top-row keys only.

2. **Emoji mode transition**
   - What we know: Currently, `KeyboardView` switches to `EmojiPickerView` via `@State currentLayer == .emoji`.
   - What's unclear: How to handle the transition when the key layer is UIKit. Does the UIKit view get hidden while emoji picker shows?
   - Recommendation: Control visibility in KeyboardRootView -- when `isEmojiMode`, hide the `KeyboardUIView` and show `EmojiPickerView`. The emoji picker stays SwiftUI.

3. **Globe key (advanceToNextInputMode)**
   - What we know: `controller.advanceToNextInputMode()` must be called from the UIInputViewController.
   - What's unclear: Whether this works when called from a UIButton action closure that captures the controller reference.
   - Recommendation: Pass the action as a closure from Coordinator (which holds the controller reference). This should work -- it's just a method call.
