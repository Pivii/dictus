# Phase 15.6: Keyboard Polish & Zero Dead Zones (Issue #59) - Research

**Researched:** 2026-03-26
**Domain:** UIKit touch routing, keyboard layout, hit-test chain, key popup visuals
**Confidence:** HIGH

## Summary

The dead zone problem has a clear root cause and a proven solution pattern. The current architecture uses UIStackView for layout with `point(inside:with:)` overrides on individual buttons to expand touch areas. However, UIStackView's internal hitTest implementation uses `subview.frame.contains(point)` -- it never calls `point(inside:with:)` on subviews. This means the negative touchInsets expansions are bypassed by UIStackView even though the custom `KeyboardRowStackView.hitTest` override was added to work around this. The fallback in `KeyboardContainerView.hitTest` (nearest-button-by-distance) catches missed touches but routes them through a different code path where `touchesBegan` fires on the button found by distance rather than the button originally hit-tested -- producing degraded feedback (haptic on touchUp instead of touchDown, no popup).

The proven solution is the **ForwardingView / single touch surface** pattern, used by `tasty-imitation-keyboard` (the most-forked open-source iOS keyboard on GitHub, 1400+ stars). Instead of relying on UIKit's hit-test chain to route touches through the UIStackView hierarchy, a single transparent overlay view intercepts ALL touches and routes them to the nearest key by Euclidean distance. This eliminates dead zones entirely and guarantees every touch takes the same code path (consistent touchDown feedback). UIStackView is kept for layout only (no touch interaction).

**Primary recommendation:** Add a `KeyboardTouchForwardingView` as a transparent overlay on top of the UIStackView layout. This view intercepts all touches, finds the nearest button by distance, and forwards touch events (touchesBegan/Moved/Ended/Cancelled) directly to that button. Disable `isUserInteractionEnabled` on all UIStackViews. Keep buttons as rendering-only subviews that still handle their own touchesBegan logic (haptic, audio, popup) when forwarded touches arrive.

## Architecture Patterns

### Recommended Approach: Touch Forwarding View (Single Touch Surface)

**What:** A transparent UIView placed on top of the entire keyboard layout that intercepts all touches and forwards them to the nearest key button by Euclidean distance. UIStackViews have `isUserInteractionEnabled = false` so they never participate in hit-testing.

**Why this approach wins over alternatives:**

| Approach | Dead Zones? | Edge Feedback? | Complexity | Gesture Compat |
|----------|-------------|----------------|------------|----------------|
| UIStackView hitTest override (current) | Reduced but not zero | Degraded path | Medium | Native |
| ForwardingView overlay (recommended) | Zero | Consistent path | Medium | Requires forwarding |
| Replace UIStackView with manual frames | Zero | Consistent if done right | High (rewrite) | Native |
| ProximityGrid + KeyDecoder | Zero | Consistent | High (over-engineered) | Requires custom |

**Why NOT manual frame layout:** Replacing UIStackView with manual frame calculations in `layoutSubviews` would eliminate the UIStackView hitTest problem, but is a larger rewrite for the same result. The touch forwarding overlay achieves zero dead zones with less disruption to the existing layout code. UIStackView remains excellent for proportional layout -- the problem is only its touch routing.

**Why NOT ProximityGrid/KeyDecoder:** The issue-56 report's ProximityGrid approach builds a spatial grid for O(1) key lookup. This is valuable for swipe-typing keyboards that process hundreds of touch points per second. For a tap keyboard, iterating ~30-40 buttons per touch event with squared-distance comparison is trivially fast (< 0.1ms). The complexity is not justified.

### Pattern: ForwardingView Implementation

**Source:** `tasty-imitation-keyboard` (GitHub, 1400+ stars) -- the most-forked open-source iOS keyboard, uses this exact pattern.

**How it works:**
1. `KeyboardTouchForwardingView` is a transparent UIView added as the topmost subview of `KeyboardContainerView`
2. Its frame matches the container's bounds (set in `layoutSubviews`)
3. All UIStackViews have `isUserInteractionEnabled = false`
4. All buttons have `isUserInteractionEnabled = false` (they no longer participate in hitTest)
5. The forwarding view overrides `touchesBegan/Moved/Ended/Cancelled`
6. On each touch event, it finds the nearest button by distance
7. It calls the button's `touchesBegan/Moved/Ended/Cancelled` directly, forwarding the touch

**Critical detail:** The forwarding view does NOT use `sendActions(for:)` or UIControl event dispatch. It calls `touchesBegan` etc. directly on the button, which preserves the full existing touch handling code (haptic on touchDown, audio, popup state, accent long-press timer, delete repeat, space trackpad).

**Key data structure:**
```swift
class KeyboardTouchForwardingView: UIView {
    /// Flat array of all touchable buttons, populated after buildKeys()
    var allButtons: [UIView] = []

    /// Track which button each active touch is currently targeting
    private var touchToButton: [UITouch: UIView] = [:]

    override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent?) {
        for touch in touches {
            let point = touch.location(in: self)
            if let nearest = findNearestButton(to: point) {
                touchToButton[touch] = nearest
                let converted = touch.location(in: nearest)
                // Create a synthetic touch set and forward
                nearest.touchesBegan(touches, with: event)
            }
        }
    }

    private func findNearestButton(to point: CGPoint) -> UIView? {
        var best: UIView?
        var bestDist: CGFloat = .greatestFiniteMagnitude
        for button in allButtons {
            let center = button.superview!.convert(button.center, to: self)
            let dx = point.x - center.x
            let dy = point.y - center.y
            let dist = dx * dx + dy * dy  // squared distance, skip sqrt
            if dist < bestDist {
                bestDist = dist
                best = button
            }
        }
        return best
    }
}
```

### Preserving Complex Gesture Behaviors

The forwarding view MUST handle these gesture patterns correctly:

| Gesture | Current Implementation | Forwarding Strategy |
|---------|----------------------|---------------------|
| Accent long-press (400ms) | LetterKeyButton.touchesBegan starts Task timer, touchesEnded checks longPressFired | Forward touchesBegan to nearest letter button. touchesMoved stays on same button (no re-routing). touchesEnded forwarded to same button. Timer fires naturally. |
| Delete repeat acceleration | DeleteKeyButton.touchesBegan starts repeat Task, touchesEnded cancels | Same as accent: forward began/ended to same button. Repeat loop runs on button. |
| Space trackpad | SpaceKeyButton.touchesBegan starts 400ms timer, touchesMoved handles drag | Forward all move events to the same space button (do NOT re-route moves to other keys when finger drags off space bar during trackpad mode). |
| Shift double-tap | ShiftKeyButton uses Date timestamp comparison | Each tap is a separate began/ended cycle. Double-tap detection works naturally. |
| Accent popup drag selection | LetterKeyButton.touchesMoved tracks finger over accent strip | Forward moves to same letter button. The button's own touchesMoved computes accent index from position. |

**Critical rule:** Once a touch begins on a button, ALL subsequent move/end/cancel events for that touch go to the SAME button. Do NOT re-route mid-touch. This is how `tasty-imitation-keyboard`'s ForwardingView works and it preserves all gesture state.

### Anti-Patterns to Avoid
- **Re-routing touchesMoved to nearest button:** Would break trackpad drag, accent popup selection, and delete repeat. Each touch sticks to its initial button.
- **Using UIControl.sendActions(for:):** Bypasses touchesBegan which is where haptic/audio/popup logic lives. Must call touchesBegan directly.
- **Keeping isUserInteractionEnabled=true on buttons:** Would create race conditions between the forwarding view and UIKit's built-in hit-test chain.
- **Complex proximity grids for a tap keyboard:** Over-engineering. Linear scan of 30-40 buttons is fast enough.

## Common Pitfalls

### Pitfall 1: Touch forwarding creates UITouch ownership issues
**What goes wrong:** Calling `button.touchesBegan(touches, with: event)` passes the original UITouch object. UIKit internally tracks which view "owns" each touch. If the forwarding view is the hit-test result but the button receives touchesBegan, UIKit may send touchesCancelled to the button because the touch's "view" property points to the forwarding view, not the button.
**Why it happens:** UIKit's responder chain expects the hit-test winner to handle touches.
**How to avoid:** Instead of forwarding raw UITouch objects, have the forwarding view call CUSTOM methods on the buttons (e.g., `handleTouchDown(at: CGPoint)`, `handleTouchMoved(at: CGPoint)`, `handleTouchUp(at: CGPoint)`). This bypasses UIKit's touch ownership tracking entirely. The buttons already have all their logic in touchesBegan/Ended -- extract the LOGIC into separate methods and call those.
**Warning signs:** Random touchesCancelled calls, buttons getting "stuck" in pressed state.

### Pitfall 2: Edge touch still not getting touchDown feedback
**What goes wrong:** The current hitTest fallback in KeyboardContainerView finds the nearest button but returns it from hitTest. This means UIKit delivers touchesBegan to that button, but the touch coordinate in the button's local space is OUTSIDE the button's bounds (because the touch was in the padding zone). Some UIButton internal logic may behave differently for out-of-bounds touches.
**Why it happens:** The current fallback returns a button from hitTest, but the touch point is outside that button's frame.
**How to avoid:** With the forwarding view approach, the forwarding view calls custom methods with the touch point, so there is no "out of bounds" concept.

### Pitfall 3: Popup position calculation breaks with forwarding view
**What goes wrong:** `LetterKeyButton.frameInKeyboardCoordinateSpace()` walks up the view hierarchy to find the container. If buttons are no longer receiving "real" touches, the popup position calculation still needs to work.
**How to avoid:** The `frameInKeyboardCoordinateSpace()` method uses `convert(bounds, to: target)` which works regardless of touch handling. It depends on the button's position in the view hierarchy, which does not change with the forwarding view pattern.

### Pitfall 4: Recording overlay touch blocking
**What goes wrong:** The recording overlay (SwiftUI) sits in a ZStack above the keyboard. It has `.allowsHitTesting(false)` when not visible, but if the forwarding view is the topmost UIKit subview, the SwiftUI overlay might intercept touches before they reach UIKit.
**How to avoid:** The recording overlay uses `.allowsHitTesting(false)` when not recording. Verify this still works after adding the forwarding view. The forwarding view lives INSIDE the UIViewRepresentable, below the SwiftUI overlay layer.

## Code Examples

### Example 1: Touch forwarding view with custom method dispatch

```swift
// Source: Pattern derived from tasty-imitation-keyboard ForwardingView
// Adapted for Dictus button architecture

class KeyboardTouchForwardingView: UIView {
    var allButtons: [UIView] = []
    private var touchToButton: [UITouch: UIView] = [:]

    override func hitTest(_ point: CGPoint, with event: UIEvent?) -> UIView? {
        // Always claim the touch if within bounds
        guard !isHidden, isUserInteractionEnabled, alpha > 0.01 else { return nil }
        guard self.point(inside: point, with: event) else { return nil }
        return self
    }

    override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent?) {
        for touch in touches {
            let point = touch.location(in: self)
            guard let button = findNearestButton(to: point) else { continue }
            touchToButton[touch] = button

            if let letter = button as? LetterKeyButton {
                letter.handleForwardedTouchDown(touch: touch, in: self)
            } else if let special = button as? BaseSpecialKeyButton {
                special.handleForwardedTouchDown(touch: touch, in: self)
            }
        }
    }

    override func touchesMoved(_ touches: Set<UITouch>, with event: UIEvent?) {
        for touch in touches {
            guard let button = touchToButton[touch] else { continue }
            // Always forward to SAME button -- preserves gesture state
            if let letter = button as? LetterKeyButton {
                letter.handleForwardedTouchMoved(touch: touch, in: self)
            } else if let special = button as? BaseSpecialKeyButton {
                special.handleForwardedTouchMoved(touch: touch, in: self)
            }
        }
    }

    override func touchesEnded(_ touches: Set<UITouch>, with event: UIEvent?) {
        for touch in touches {
            guard let button = touchToButton[touch] else { continue }
            if let letter = button as? LetterKeyButton {
                letter.handleForwardedTouchUp()
            } else if let special = button as? BaseSpecialKeyButton {
                special.handleForwardedTouchUp()
            }
            touchToButton[touch] = nil
        }
    }

    override func touchesCancelled(_ touches: Set<UITouch>, with event: UIEvent?) {
        for touch in touches {
            guard let button = touchToButton[touch] else { continue }
            if let letter = button as? LetterKeyButton {
                letter.handleForwardedTouchCancelled()
            } else if let special = button as? BaseSpecialKeyButton {
                special.handleForwardedTouchCancelled()
            }
            touchToButton[touch] = nil
        }
    }

    private func findNearestButton(to point: CGPoint) -> UIView? {
        var best: UIView?
        var bestDist: CGFloat = .greatestFiniteMagnitude
        for button in allButtons {
            guard let parent = button.superview else { continue }
            let center = parent.convert(button.center, to: self)
            let dx = point.x - center.x
            let dy = point.y - center.y
            let dist = dx * dx + dy * dy
            if dist < bestDist {
                bestDist = dist
                best = button
            }
        }
        return best
    }
}
```

```swift
// MARK: - Forwarded touch handling (called by KeyboardTouchForwardingView)

func handleForwardedTouchDown(touch: UITouch, in sourceView: UIView) {
    let touchDownState = KeyTapSignposter.beginTouchDown()

    // Visual highlight
    backgroundView.backgroundColor = Self.pressedBackground
    KeyTapSignposter.emitHighlight(touchDownState)

    // Audio + haptic on touchDown
    AudioServicesPlaySystemSound(KeySound.letter)
    HapticFeedback.keyTapped()
    KeyTapSignposter.emitHaptic(touchDownState)
    HapticFeedback.prepareForNextTap()
    KeyTapSignposter.endTouchDown(touchDownState)

    // Popup preview
    let frameInKeyboard = frameInKeyboardCoordinateSpace()
    touchState?.showPress(label: displayLabel, frame: frameInKeyboard)

    // Accent long-press timer
    longPressFired = false
    longPressTimer?.cancel()
    longPressTimer = Task { @MainActor [weak self] in
        try? await Task.sleep(nanoseconds: 400_000_000)
        guard !Task.isCancelled else { return }
        self?.handleLongPress()
    }
}

func handleForwardedTouchMoved(touch: UITouch, in sourceView: UIView) {
    // Accent popup tracking (same logic as current touchesMoved)
    guard longPressFired, touchState?.showingAccents == true else { return }
    let location = touch.location(in: self)
    // ... same accent index calculation as existing touchesMoved
}

func handleForwardedTouchUp() {
    longPressTimer?.cancel()
    longPressTimer = nil
    backgroundView.backgroundColor = Self.normalBackground

    if let state = touchState, state.showingAccents,
       let index = state.selectedAccentIndex,
       index >= 0, index < state.accentOptions.count {
        onTap?(state.accentOptions[index])
        touchState?.hideAccents()
    } else if !longPressFired {
        onTap?(outputChar)
    }

    touchState?.hidePress()
    touchState?.hideAccents()
    longPressFired = false
}

func handleForwardedTouchCancelled() {
    longPressTimer?.cancel()
    longPressTimer = nil
    backgroundView.backgroundColor = Self.normalBackground
    touchState?.hidePress()
    touchState?.hideAccents()
    longPressFired = false
}
```

### Example 3: Key popup polish -- wider stem connected to key base

```swift
// Updated KeyPopupShape with wider stem base matching key width
struct KeyPopupShape: Shape {
    var cornerRadius: CGFloat = 6
    var stemBaseWidth: CGFloat = 38  // Wide enough to match key visual width
    var stemHeight: CGFloat = 8

    func path(in rect: CGRect) -> Path {
        let bubbleRect = CGRect(x: rect.minX, y: rect.minY,
                                width: rect.width, height: rect.height - stemHeight)

        var path = Path()

        // Rounded rectangle bubble
        path.addRoundedRect(in: bubbleRect,
                           cornerSize: CGSize(width: cornerRadius, height: cornerRadius))

        // Stem: wide at base (connecting to key), tapers to bubble width
        // The stem base should be as wide as the key's visual background
        let midX = rect.midX
        let stemTop = bubbleRect.maxY
        let stemBottom = rect.maxY
        let bubbleHalfWidth = min(rect.width / 2, stemBaseWidth / 2 + 4)
        let baseHalfWidth = stemBaseWidth / 2

        path.move(to: CGPoint(x: midX - bubbleHalfWidth, y: stemTop))
        path.addLine(to: CGPoint(x: midX - baseHalfWidth, y: stemBottom))
        path.addLine(to: CGPoint(x: midX + baseHalfWidth, y: stemBottom))
        path.addLine(to: CGPoint(x: midX + bubbleHalfWidth, y: stemTop))
        path.closeSubpath()

        return path
    }
}

// Updated KeyPopup with larger letter
struct KeyPopup: View {
    let label: String

    // Larger font for popup letter (Apple shows ~1.5x key font size)
    private let popupFontSize: CGFloat = 34  // Up from 26 (key is 22)
    private let bubbleHeight: CGFloat = 42
    private let stemHeight: CGFloat = 8

    var body: some View {
        ZStack(alignment: .top) {
            KeyPopupShape(stemBaseWidth: 38, stemHeight: stemHeight)
                .fill(KeyMetrics.letterKeyColor)
                .shadow(color: .black.opacity(0.2), radius: 3, x: 0, y: 2)

            Text(label)
                .font(.system(size: popupFontSize, weight: .light))
                .foregroundStyle(.primary)
                .frame(width: 44, height: bubbleHeight)
        }
        .frame(width: 44, height: bubbleHeight + stemHeight)
    }
}
```

## Root Cause Analysis: Dead Zones

### Why dead zones persist despite all the hitTest overrides

The debug diagnosis in `.planning/debug/dead-zones-uikit-keyboard.md` extensively analyzed the layout and concluded button frames tile perfectly (spacing=0, distribution=.fill/.fillEqually). The real issue is confirmed by the OpenRadar bug report (Radar 30592429, 2017, still open):

**UIStackView consumes touches that don't hit any subview.** When a touch lands in a UIStackView's bounds but no arranged subview claims it, the stack view returns `self` from hitTest instead of `nil`. This prevents the touch from falling through to the parent's fallback handler.

The existing `KeyboardRowStackView` override partially fixes this by calling `point(inside:with:)` on subviews. But the `mainStack` (vertical UIStackView) is NOT overridden -- it still uses default UIStackView hitTest. When a touch falls in the 4pt rowSidePadding zone or at row boundaries, the mainStack itself swallows it.

The `KeyboardContainerView.hitTest` fallback catches some cases (when `super.hitTest` returns a non-button view), but the found button receives the touch through a different path: hitTest returns the button, then UIKit delivers touchesBegan to it. However the touch point in the button's coordinate space may be outside its bounds, and UIButton may handle this differently internally.

**The forwarding view eliminates ALL of these problems** by removing UIStackView from the touch chain entirely.

### Why edge touch feedback is degraded

When the `KeyboardContainerView.hitTest` fallback routes a touch to the nearest button:
1. hitTest returns the button
2. UIKit calls `touchesBegan` on the button with the original touch
3. The touch's `location(in: button)` is outside the button's bounds (the touch was in the padding zone)
4. The button's `super.touchesBegan` (UIButton) may handle out-of-bounds touches differently -- possibly delaying or skipping the normal `.touchDown` control event
5. The button's custom touchesBegan code still runs, but UIButton internal state may not be consistent

With the forwarding view, the custom `handleForwardedTouchDown` method runs immediately on the nearest button, with no UIButton internal state confusion.

## Open Questions

1. **UITouch forwarding vs custom method dispatch**
   - What we know: Calling `button.touchesBegan(touches, with: event)` directly may cause UIKit touch ownership conflicts. `tasty-imitation-keyboard` uses `handleControl` + `sendActions(for:)` which works for UIControl events but skips touchesBegan logic.
   - What's unclear: Whether the Dictus buttons' custom touchesBegan logic will work correctly when called by the forwarding view, or whether extraction to separate methods is strictly necessary.
   - Recommendation: Extract touch logic into separate `handleForwardedTouchDown/Moved/Up/Cancelled` methods. This is safer and avoids any UIKit internal state issues. It also makes the code more testable.

2. **Multi-touch handling**
   - What we know: The forwarding view must handle multiple simultaneous touches (e.g., holding shift while typing a letter).
   - What's unclear: Whether UITouch identity is stable enough for the `touchToButton` dictionary across the full touch lifecycle.
   - Recommendation: UITouch objects have stable identity within a touch session (began to ended/cancelled). The dictionary pattern is standard and used by `tasty-imitation-keyboard`.
