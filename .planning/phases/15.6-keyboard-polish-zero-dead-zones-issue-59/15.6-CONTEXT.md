# Phase 15.6: Keyboard Polish & Zero Dead Zones (Issue #59) - Context

**Gathered:** 2026-03-26
**Status:** Ready for research

<domain>
## Phase Boundary

Two goals: (1) Definitively eliminate dead zones on the UIKit keyboard so every pixel resolves to a key with full touchDown feedback. (2) Polish key popup visuals to match Apple/competitor quality. Ref: Issue #59.

Phase 15.5 rebuilt the keyboard in UIKit with UIButton subclasses and point(inside:with:) overrides, but dead zones persist because UIStackView.hitTest bypasses point(inside:with:). Multiple fix attempts (KeyboardRowStackView hitTest override, KeyboardContainerView hitTest fallback, mainStack hitTest override) reduced but did not eliminate the problem.

</domain>

<decisions>
## Implementation Decisions

### Dead zone fix approach — REQUIRES DEEP RESEARCH
- **Status:** Not decided. Research phase must investigate thoroughly before choosing.
- **Reference architecture:** The issue-56 report (`assets/reference/issue-56-report.md` at commit 99300f9) recommends a "single touch surface + proximity grid" approach inspired by AOSP LatinIME, Apple patent US8232973B2, and AnySoftKeyboard. This was written when the keyboard was SwiftUI — now that we're UIKit, more options are available.
- **Research mandate:** The researcher agent MUST do extensive internet research on:
  - Open-source iOS keyboard implementations that have solved dead zones (KeyboardKit, NuType, Fleksy clones, any Swift keyboard on GitHub)
  - How UIStackView hitTest works internally and proven workarounds
  - Whether replacing UIStackView with manual frame layout solves the problem simply
  - Whether a single-view touch dispatcher (from issue-56 report) is the right approach now that we have UIKit buttons
  - How to preserve complex gesture behaviors (accent long-press 400ms, delete repeat acceleration, space trackpad, shift double-tap) with whichever approach is chosen
- **Constraint:** The current UIKit button subclasses (LetterKeyButton, BaseSpecialKeyButton and subclasses) handle rendering well. The problem is touch routing, not rendering. The solution may keep buttons as display-only and add a touch routing layer, or may fix the hit-test chain, or may replace UIStackView layout — research decides.
- **Prior failed approaches (from Phase 15.4 memory):**
  - 16 SwiftUI approaches failed (documented in issue #56)
  - Phase 15.5 UIKit approach: point(inside:with:) with negative touchInsets — bypassed by UIStackView.hitTest
  - KeyboardRowStackView hitTest override — partial fix
  - KeyboardContainerView hitTest fallback to nearest button — partial fix
  - Recording overlay visibility toggle via container.isHidden — working

### Two distinct bugs to solve
1. **Dead zones** — Tap in visual gap between keys → nothing happens (no haptic, no letter, no popup). Must become zero.
2. **Edge touch degraded feedback** — Tap on the outer edge of a border key (e.g., left side of A, right side of P) → letter inserts correctly BUT haptic fires on touchUp instead of touchDown, and no popup appears. This is a different flow than dead zones — the key IS hit, but through a degraded path (likely the hitTest fallback routing the touch differently than a direct touchesBegan on the button). PR #57 had fixed this in SwiftUI; must be fixed in UIKit too.
- Both bugs may share a root cause (touch routing path) or may be separate. Research should investigate.

### Key popup visual polish
- **Current state:** Popup works, has a stem shape, not clipped on first row. Functional but needs visual polish.
- **Changes needed:**
  1. **Bigger letter in popup** — Currently the popup letter is the same size as the key letter. Apple and competitors show a LARGER letter in the popup. Increase font size in the popup bubble.
  2. **Wider stem in contact with key base** — The stem should be wide enough to visually connect with the top of the pressed key. No gap or separation between the popup and the key below. They must look like ONE continuous shape.
  3. **Keep current popup height** — Do not change the overall height of the popup. Only adjust the letter size and stem width/connection.
- **Claude's discretion:** Exact font size increase, exact stem width, how to achieve the seamless connection (shared background color, overlapping shapes, etc.)

### Phase 15.3 optimizations — verification only
- **No visual tuning needed.** Colors, timing values, signposter wiring = keep as-is.
- **The edge touch feedback bug (gray area 3) is covered by the "edge touch degraded feedback" item above.** Once the touch routing is fixed, edge keys should get the same touchDown flow as center keys.
- **Performance verification:** After dead zone fix is implemented, verify that keyboard responsiveness is at least as good as Phase 15.3 SwiftUI keyboard. No specific metric target — just verify no regression in perceived latency.

### What is NOT in scope
- Accent strip edge clamping — already working (fixed in 15.5-05)
- Emoji picker layout — already working (fixed in 15.5-05)
- Special key icons (shift, delete, return, emoji) — already working (fixed in 15.5-04)
- Layer switching (123/ABC/#+=) — already working (fixed in 15.5-04)
- Return key context adaptation — already working (fixed in 15.5-04)
- Delete haptic gating on empty text — already working (fixed in 15.5-04)

## Existing Code Insights

### Reusable Assets
- `KeyMetrics` enum — all spacing constants (keyHeight, rowSpacing, keySpacing, rowSidePadding, keyCornerRadius) with 3 device classes
- `DeviceClass` enum — compact/standard/large breakpoints at 667/852pt screen height
- `KeyboardLayout` — AZERTY/QWERTY row definitions as `[[KeyDefinition]]`
- `KeyDefinition` — key type, label, output, widthMultiplier
- `AccentedCharacters` — accent data per key for long-press
- `HapticFeedback` — pre-allocated UIImpactFeedbackGenerator instances
- `KeySound` enum — system sound IDs (letter: 1104, delete: 1155, modifier: 1156)
- `KeyTapSignposter` — OSSignposter for Instruments profiling
- ProximityGrid/KeyDecoder from git history (commits 83767f6..f201d1a) — may be reusable

### Current Architecture
- KeyboardContainerView (UIView) → mainStack (UIStackView, vertical) → 4x KeyboardRowStackView (UIStackView, horizontal) → UIButton subclasses
- mainStack inset by rowSidePadding (3-5pt) from container edges
- Button frames tile perfectly within rows (spacing=0, proportional widths)
- Visual gaps created by backgroundView inset (keySpacing/2 horizontal, rowSpacing/2 vertical)
- point(inside:with:) overrides with negative touchInsets — BYPASSED by UIStackView.hitTest
- KeyboardContainerView.hitTest fallback finds nearest button when UIStackView misses — PARTIAL fix (works but degraded feedback path)
- KeyboardInputView.hitTest prioritizes UIKit container over SwiftUI hosting view

### Integration Points
- KeyboardRootView ZStack — popup/accent overlays positioned using KeyboardTouchState
- KeyboardTouchState bridges UIKit button press state to SwiftUI overlay rendering
- insertCharacter() pipeline — audio/haptic/text insertion, called from button touchesEnded
- SuggestionState.update(proxy:) — called after keystroke, runs on background queue

<specifics>
## Specific Ideas

- Pierre explicitly wants MAXIMUM internet research on dead zones — this is the hardest bug and the #1 priority
- The issue-56 report's "single touch surface" approach may be the right architecture now that we're in UIKit, but research should validate
- The edge touch degraded feedback is a distinct symptom from dead zones — same key, different touch path produces different feedback timing
- Popup polish is cosmetic and straightforward — don't over-engineer it
- Performance must not regress from Phase 15.3 level — verify after implementation

</specifics>

<deferred>
## Deferred Ideas

- Probabilistic key selection with language model priors (from issue-56 report) — interesting but overkill for current needs. Simple nearest-key resolution is sufficient.
- Sweet spot calibration per row (thumb reach bias) — future optimization, not needed for zero dead zones
- Hystéresis for touch tracking — may not be needed for tap-only keyboard (no swipe typing)

</deferred>
