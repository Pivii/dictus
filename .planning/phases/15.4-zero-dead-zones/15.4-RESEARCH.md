# Phase 15.4: Zero Dead Zones - Research

**Researched:** 2026-03-24
**Domain:** SwiftUI keyboard extension touch handling, dead zone elimination
**Confidence:** HIGH

## Summary

Phase 15.4 eliminates dead zones between keyboard keys so every pixel of the keyboard surface resolves to a key. The user has locked an **incremental approach**: keep per-key DragGestures, improve the existing `handleDeadZoneTap()` catch-all on the VStack background, and validate with temporary logging before any structural changes.

The current architecture already handles most touches correctly. Keys use `HStack(spacing: 0)` with `contentShape(Rectangle())`, meaning key frames are adjacent with no layout gaps. Dead zones exist only in the visual padding/margin areas: `rowSidePadding` (3-5pt per side), `keySpacing/2` inset on backgrounds (not frames), and `rowSpacing/2` inset at row boundaries. The catch-all DragGesture on the parent VStack fires for these gap touches but its `handleDeadZoneTap()` resolution logic needs improvement for edge cases (side margins, row boundaries).

Three prior attempts failed not because of resolution logic but because of touch delivery issues with UIViewRepresentable in keyboard extensions (iOS clips the bottom ~35%). The locked approach avoids this entirely by staying 100% SwiftUI with the existing DragGesture pattern.

**Primary recommendation:** Add version/build logging (issue #58), then add temporary touch coordinate logging to the catch-all, verify it fires in all gap areas, improve `handleDeadZoneTap()` resolution for margin/boundary cases, validate with systematic UAT, then remove temporary logs.

## Architecture Patterns

### Current Touch Architecture (DO NOT CHANGE)

```
KeyboardView (GeometryReader)
  ZStack
    VStack(spacing: 0)                          <-- catch-all .gesture() here
      ForEach rows
        KeyRow (HStack spacing: 0, .padding(.horizontal, rowSidePadding))
          KeyButton / ShiftKey / DeleteKey / ... <-- per-key DragGesture(minimumDistance: 0)
            .frame(maxWidth: .infinity)
            .frame(height: keyHeight + rowSpacing)
            .contentShape(Rectangle())
```

**Key insight:** With `HStack(spacing: 0)`, key *frames* are contiguous. Dead zones exist only in:
1. `rowSidePadding` margins (3-5pt on each side, OUTSIDE the HStack padding)
2. Visual gap between key *backgrounds* (the `keySpacing/2` padding on RoundedRectangle backgrounds -- but the frame and contentShape cover this)
3. Row boundaries: the VStack has `spacing: 0` and each key's frame height = `keyHeight + rowSpacing`, so row frames should be contiguous vertically

**Where the catch-all fires:** Touches that start in the `.padding(.horizontal, rowSidePadding)` area outside the HStack's key frames, or at exact gesture recognizer boundaries between adjacent keys.

### Pattern 1: Improved handleDeadZoneTap Resolution

**What:** The current `handleDeadZoneTap(at:rowWidth:)` already does row detection (Y / rowHeight) and key detection (X walk). Improvements needed:

1. **Side margin handling:** If `point.x < rowSidePadding`, resolve to first key. If `point.x > rowWidth - rowSidePadding`, resolve to last key. Current code starts `x = rowSidePadding` and walks forward, so left margin touches correctly fall through to `targetKey = row.last!` default -- but this is WRONG (should be first key, not last).

2. **Row boundary clamping:** Current `max(0, min(Int(point.y / rowHeight), currentRows.count - 1))` is correct but could be off by half a row spacing at boundaries. The formula works because key frames include rowSpacing.

**Current bug in handleDeadZoneTap:**
```swift
// BUG: Left margin (point.x < rowSidePadding) never enters the if-branch
// because x starts at rowSidePadding and point.x < x + keyWidth is true
// for the first key. Actually... wait. Let me re-read:
var x: CGFloat = KeyMetrics.rowSidePadding
// If point.x < rowSidePadding, then point.x < x + keyWidth for first key
// So it correctly resolves to first key. No bug here.
// HOWEVER: if point.x > rowWidth - rowSidePadding (right margin),
// the loop runs through all keys without matching, and targetKey = row.last!
// This is CORRECT -- right margin -> last key. Both margins work.
```

After re-analysis: the current resolution logic is actually correct for margin cases. The improvement needed is for **intermediate gaps** where SwiftUI drops the touch between two adjacent DragGesture recognizers.

## Common Pitfalls

### Pitfall 1: Stale Build Confusion
**What goes wrong:** After Xcode install, the simulator/device may still run the old build. You think your changes aren't working but they aren't even deployed.
**Why it happens:** Xcode caching, keyboard extension not reloading after rebuild.
**How to avoid:** Issue #58 (version/build in logs) is the explicit prerequisite. Always check version in logs before testing.
**Warning signs:** Behavior unchanged despite code changes. Logs show old version.

### Pitfall 2: Breaking Per-Key Gestures While "Improving" Catch-All
**What goes wrong:** Changing gesture modifiers or priority inadvertently breaks the working per-key DragGestures.
**Why it happens:** SwiftUI gesture precedence is subtle. `.gesture()` vs `.highPriorityGesture()` vs `.simultaneousGesture()` behave differently.
**How to avoid:** Step 2 is log-only (no gesture changes). Step 3 only modifies the resolution function inside handleDeadZoneTap, not the gesture attachment.
**Warning signs:** Letter keys stop producing characters after a change.

### Pitfall 3: Catch-All Not Firing in Expected Areas
**What goes wrong:** The catch-all DragGesture on the parent VStack may not fire for certain gap positions because SwiftUI already assigned the touch to a child gesture.
**Why it happens:** SwiftUI gesture disambiguation assigns touches to the deepest matching gesture recognizer. At exact boundaries, the behavior is implementation-defined.
**How to avoid:** Step 2 (temporary logging) explicitly validates WHERE the catch-all fires. If it doesn't fire in certain gaps, the approach needs adjustment BEFORE proceeding to Step 3.
**Warning signs:** No log entries for taps in specific gap areas.

### Pitfall 4: Row Index Off-By-One
**What goes wrong:** Touch at exact row boundary resolves to wrong row.
**Why it happens:** Integer division `Int(point.y / rowHeight)` truncates. At boundary `y = rowHeight * 1.0`, it could be row 0 or row 1.
**How to avoid:** The current clamping `max(0, min(..., count-1))` handles out-of-bounds. For boundary ambiguity, the nearest-key approach is correct: whichever row is closer to the touch point.
**Warning signs:** Touches between rows 1 and 2 produce characters from the wrong row.

### Pitfall 5: Missing Key Types in handleDeadZoneTap Switch
**What goes wrong:** New key types added in future aren't handled by the catch-all switch statement.
**Why it happens:** The switch in handleDeadZoneTap covers all current KeyDefinition.type cases but isn't exhaustive.
**How to avoid:** Current switch already handles: character, delete, space, returnKey, shift, globe, emoji, layerSwitch, symbolToggle, accentAdaptive, mic. Verify completeness.
**Warning signs:** Compiler warning about non-exhaustive switch (Swift will warn if KeyType enum adds cases).

## Open Questions

1. **Does the catch-all fire for ALL gap positions?**
   - What we know: It fires for some gaps (per issue #56 comment: "already eliminates most dead zones")
   - What's unclear: Whether SwiftUI drops touches at exact DragGesture boundaries before the parent can catch them
   - Recommendation: Step 2 (temporary logging) answers this definitively. If it doesn't fire everywhere, the approach changes.

2. **Pre-compute vs compute-on-touch for key rectangles?**
   - What we know: Current handleDeadZoneTap computes on each touch (walk the row). This is O(n) per row where n=10-12 keys.
   - What's unclear: Whether pre-computation provides meaningful benefit
   - Recommendation: Compute on touch is fine. 10-12 iterations with CGFloat arithmetic is sub-microsecond. Pre-computation adds complexity for no user-perceptible benefit.

3. **Reuse ProximityGrid from git history or simplify?**
   - What we know: ProximityGrid provides O(1) lookup with spatial indexing. The catch-all only handles ~3-11pt gaps.
   - What's unclear: Whether the complexity of ProximityGrid is warranted for gap-only resolution
   - Recommendation: Start with improving handleDeadZoneTap directly (simpler). If logging reveals many edge cases, consider ProximityGrid as escalation.
